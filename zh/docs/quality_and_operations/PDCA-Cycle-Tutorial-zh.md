# PDCA 循环（戴明环）

很多团队都经历过这样的循环：发现问题，开会讨论，定下几条改进措施，然后就没有然后了。过一段时间，同样的问题又出现，又开一次会，又定几条措施。问题不在于大家不努力，而在于**改进本身没有形成闭环**——没有人检验措施是否真的有效，有效的做法也没有被固定下来。

**PDCA 循环（Plan-Do-Check-Act）** 就是为解决这个问题而生的。它把任何一次改进拆成四个必须走完的阶段：**计划（Plan）、执行（Do）、检查（Check）、处理（Act）**。它由统计学家沃特·休哈特（Walter Shewhart）提出雏形，经爱德华·戴明（W. Edwards Deming）在日本推广后广为人知，因此也被称为**戴明环**。它是[全面质量管理](Total-Quality-Management-Tutorial-zh.md)、[精益运营](Lean-Operations-Tutorial-zh.md)和[改善](Kaizen-Tutorial-zh.md)的共同引擎。

PDCA 的精髓不在于这四个词本身，而在于**它是一个“圈”**：第四步的结论会成为下一轮第一步的输入。每转一圈，管理水平就上升一个台阶，所以它常被画成一个沿着斜坡向上滚动的轮子——而“标准化”就是防止轮子往回滚的垫块。

!!! abstract "要点速览"

    - **四个阶段**：计划（定目标、析原因、拟方案）→ 执行（小范围试行）→ 检查（用数据比对预期）→ 处理（有效就标准化，无效就回到计划）。
    - **先小后大**：改进措施先在小范围试，验证有效再推广，这是 Do 阶段最容易被忽略的一点。
    - **Check 必须用数据**：拿实际结果和计划阶段设定的目标比，而不是问“大家感觉怎么样”。
    - **Act 的两件事**：把有效做法写进标准；把没解决的问题带入下一轮。
    - **常见搭档**：Plan 阶段用[鱼骨图](../root_cause_analysis/Fishbone-Diagram-Tutorial-zh.md)和[五问法](../root_cause_analysis/5-Whys-Tutorial-zh.md)找原因，用[帕累托分析](../decision_making/Pareto-Analysis-Tutorial-zh.md)排优先级。

## 四个阶段分别做什么

### P — 计划（Plan）

这是四个阶段里最花时间、也最决定成败的一步。它包含三件事：

1.  **定义问题和目标**：用数据描述现状和目标。“提高良品率”不是目标，“把 A 产线的良品率从 95% 提升到 98%，在 6 月底前完成”才是（参见 [SMART 目标](../goal_management/SMART-Goals-Tutorial-zh.md)）。
2.  **分析原因**：到现场看实际情况，用鱼骨图把可能原因列全，用五问法往下挖，用数据验证哪些是真正的关键原因。
3.  **制定对策**：针对验证过的关键原因，设计具体措施，并写明负责人、时间和**预期效果**。预期效果必须写下来，否则 Check 阶段就没有比较的基准。

### D — 执行（Do）

**先小范围试行**，而不是全面铺开。选一条产线、一个班组、一个门店做试点，同时**记录过程数据**：措施是否被真正执行？执行中遇到了什么阻碍？有没有产生意料之外的副作用？

这一阶段最常见的失败不是措施不对，而是措施根本没被执行到位，而事后没人知道。

### C — 检查（Check）

把实际结果和计划阶段设定的预期效果做对比，回答三个问题：

*   **目标达成了吗？**用数字说话。
*   **是这个措施带来的吗？**有没有其他因素同时在变（比如正好是淡季）？
*   **过程按计划执行了吗？**如果措施没执行到位，那么“效果不好”不能证明措施无效。

### A — 处理（Act）

根据检查结果走两条路之一：

*   **有效** → **标准化**。修订作业标准、检查清单、培训材料，让新做法成为默认做法；然后把这个经验横向推广到其他产线、班组、部门。
*   **无效或部分有效** → **回到 Plan**。重新分析原因（往往是第一轮原因找错了），设计新的对策，进入下一轮循环。

无论哪种情况，都要把**本轮没有解决的遗留问题**明确列出来，作为下一轮的输入。

## PDCA 实施模板

| 阶段 | 项目 | 内容 |
| --- | --- | --- |
| **P** | 问题陈述 | 现象、时间、影响范围（可衡量，不含原因） |
| | 目标 | 指标、基线、目标值、期限 |
| | 关键原因 | 经数据验证的 1~3 条 |
| | 对策 | 措施、负责人、完成时间 |
| | **预期效果** | 指标预计改善到多少 |
| **D** | 试点范围 | 哪条线 / 哪个班组 / 多长时间 |
| | 执行记录 | 实际执行情况、遇到的阻碍 |
| **C** | 实际结果 | 指标实际值 |
| | 与预期的差异 | 达成 / 未达成，差多少 |
| | 原因分析 | 措施无效？执行不到位？外部因素？ |
| **A** | 标准化内容 | 修订了哪份文件、谁来培训 |
| | 横向推广 | 推广到哪些单位、何时 |
| | 遗留问题 | 进入下一轮的问题清单 |

**自检清单**

- [ ] 目标有数字和期限
- [ ] 关键原因经过数据验证，不是猜测
- [ ] 计划阶段写下了预期效果
- [ ] 措施先在小范围试过
- [ ] 检查时用的是数据，不是感觉
- [ ] 有效做法已写进标准文件

## 应用案例

**案例一：降低客服工单的重复来电率**

*   **P**：现状是 32% 的客户在工单关闭后 7 天内再次来电。用鱼骨图分析后，数据验证出两个关键原因：首次回复中使用了内部术语、以及关闭工单前没有确认客户是否真正解决。目标是把重复来电率降到 20%，预期两条措施各能带来约 6 个百分点的改善。
*   **D**：在一个 8 人小组试行两周——引入术语对照表，并在关单前增加一句“您看这个方案能解决您的问题吗？”。
*   **C**：两周后该组重复来电率降到 21%，接近目标；但平均处理时长从 6.2 分钟上升到 7.0 分钟。
*   **A**：把两条措施写入客服标准话术并培训全员；处理时长上升的问题作为遗留问题，进入下一轮 PDCA（后来通过优化术语对照表的查找方式解决）。

**案例二：缩短新员工上手时间**

*   **P**：新入职工程师平均需要 6 周才能独立提交第一个生产变更。访谈发现主要卡在环境搭建和不知道找谁问。目标缩短到 3 周。
*   **D**：为新一批 5 人准备了一键环境脚本，并指定“导师 + 伙伴”两个固定联系人。
*   **C**：5 人平均 3.5 周完成首次提交，其中 4 人在 3 周内完成；唯一超时的那位卡在了权限审批流程上。
*   **A**：脚本和导师制度写入入职手册；权限审批慢作为新问题进入下一轮。

**案例三：个人应用——改善跑步习惯**

*   **P**：目标是一个月内把每周跑步次数从 1 次提升到 3 次。分析后发现障碍是下班后太累、装备要现找。
*   **D**：改到早晨跑，前一晚把装备放在门口，试行两周。
*   **C**：两周内跑了 5 次（计划 6 次），缺的那次是因为前一天熬夜。
*   **A**：把“前一晚备好装备”固定下来；针对熬夜问题，下一轮增加一条“23 点后不看手机”的措施。

## 常见误区

1.  **只有 P 和 D，没有 C 和 A**。这是最普遍的问题：措施定了、也做了，但没人回头检验效果，更没有把有效做法固化。没有 C 和 A 的 PDCA 只是“计划—执行”，不是循环。
2.  **计划阶段不写预期效果**。没有预期，检查阶段就无从比较，只能变成“感觉好像好一点”。
3.  **跳过小范围试点**。直接全面推广，一旦措施有问题，影响面大、回退成本高。
4.  **把“执行不到位”当成“措施无效”**。检查时必须先确认措施是否被真正执行，否则会误杀好方案。
5.  **有效了却不标准化**。改进成果依赖某几个人的自觉，人一换就退回原样。标准化是防止轮子回滚的垫块。
6.  **一轮就想解决所有问题**。PDCA 的价值在于多转几圈，每圈解决一两个关键问题。

## PDCA、OODA 与 DMAIC 的区别

| | PDCA | OODA 循环 | DMAIC |
| --- | --- | --- | --- |
| 全称 | 计划-执行-检查-处理 | 观察-调整-决策-行动 | 定义-测量-分析-改进-控制 |
| 来源 | 质量管理（休哈特、戴明） | 军事（约翰·博伊德） | [六西格玛](Six-Sigma-Tutorial-zh.md) |
| 核心诉求 | 持续改进、固化成果 | 在对抗环境中比对手更快决策 | 用统计方法消除变异 |
| 节奏 | 中等，以周/月为单位 | 极快，以秒/分钟为单位 | 慢，一个项目 3~6 个月 |
| 适合场景 | 日常改进、流程优化 | 竞争对抗、应急响应 | 复杂质量问题、需要统计分析 |

可以这样理解：**DMAIC 是 PDCA 的加强版**（在 Plan 阶段加入了严格的测量和统计分析），而 **OODA 是 PDCA 的高速版**（面向对抗环境，强调决策速度）。

## 常见问题

??? question "PDCA 和 PDSA 有什么区别？"

    戴明后期更倾向于用 **PDSA（Plan-Do-Study-Act）**，把 Check 换成 Study。他认为 "Check" 容易被理解成“检查有没有做”，而 "Study" 强调的是“研究结果说明了什么”。两者流程一致，PDSA 更强调从结果中学习。

??? question "一个 PDCA 循环应该持续多久？"

    没有固定时长，取决于改进的规模和指标的反馈周期。班组层面的小改进可能一两周转一圈；流程性改进常见一到三个月。原则是：**一圈要短到能快速看到结果，长到足以让指标产生有意义的变化**。

??? question "PDCA 和改善（Kaizen）是什么关系？"

    改善是“持续小步改进”的理念和文化，PDCA 是实现它的标准方法。可以说改善回答“为什么要持续改进”，PDCA 回答“一次改进应该怎么走完”。

??? question "PDCA 只能用在制造业吗？"

    不是。它适用于任何有目标、有流程、结果可衡量的场景：客服、软件开发、医院护理、教学、市场活动，乃至个人习惯养成。本文的三个案例分别来自客服、软件和个人生活。

??? question "检查阶段发现没效果，是不是说明这次 PDCA 失败了？"

    不是。排除了“执行不到位”之后，“措施无效”本身就是一个有价值的结论：它排除了一个错误假设，让下一轮更接近真正的原因。PDCA 的目标是学习，不是每轮都成功。
