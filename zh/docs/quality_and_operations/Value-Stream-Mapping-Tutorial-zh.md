# 价值流图（Value Stream Mapping）

一个订单从下单到交付要 21 天，团队该怎么改进？常见做法是让每个环节都「再快一点」——但很多时候，21 天里真正在干活的时间只有 3 小时，剩下的全是**等待**。在这种情况下，让员工手速提升 20% 毫无意义。

**价值流图（Value Stream Mapping，VSM）** 就是用来揭示这个真相的工具。它把一个流程从头到尾画在一张纸上，包括：每个环节做什么、耗时多久、中间积压了多少、信息怎么流转。画完之后，**增值时间和总前置时间的巨大落差**通常会让所有人震惊——而这个落差，就是改进空间。

VSM 源自丰田生产系统的「物与信息流图」，是[精益运营](Lean-Operations-Tutorial-zh.md)的核心工具。它和普通流程图最大的区别是：**流程图只画步骤，价值流图同时画出等待、库存和信息流，并带上数据**。

!!! abstract "要点速览"

    - **画两张图**：现状图（真实发生的）和未来图（改进目标），中间是行动计划。
    - **三个流必须都画**：物料流（从左到右）、信息流（从右到左）、时间线（最底部）。
    - **核心指标**：增值时间 ÷ 总前置时间 = 增值比。多数流程低于 5%。
    - **用脚画，不要用脑画**：到现场走一遍，用秒表和实际数据，不要用流程文档里写的理想值。
    - **瓶颈通常在等待和交接处**，不在某个人干活慢。

## 价值流图的组成

一张标准的价值流图有三层：

| 层次 | 位置 | 内容 |
| --- | --- | --- |
| **信息流** | 上方，从右向左 | 客户需求如何传递到各环节：订单、排产计划、看板信号 |
| **物料流 / 工作流** | 中部，从左向右 | 每个处理环节，以及环节之间的积压（库存三角） |
| **时间线** | 底部，阶梯状 | 上台阶 = 增值时间；下台阶 = 等待时间 |

每个处理环节下面要标注**数据框**，常见指标：

| 指标 | 含义 |
| --- | --- |
| **C/T（周期时间）** | 处理一个单位实际花费的时间 |
| **C/O（换型时间）** | 从处理一种任务切换到另一种所需的时间 |
| **可用时间** | 该环节每天实际可工作的时间 |
| **良品率 / 一次通过率** | 不需要返工就通过的比例 |
| **在制品（WIP）** | 环节之间积压的数量 |

## 关键指标：增值比

| 指标 | 定义 |
| --- | --- |
| **增值时间（VA）** | 客户愿意为之付钱的时间，即真正改变产品或服务状态的时间 |
| **非增值时间（NVA）** | 等待、搬运、返工、审批排队等时间 |
| **前置时间（Lead Time）** | 从流程开始到结束的总时间 |
| **增值比** | 增值时间 ÷ 前置时间 |

**大多数未经优化的流程，增值比在 1%~5% 之间。** 这意味着：与其让那 3% 的时间更快，不如去消灭那 97% 的等待。这是价值流图最重要的洞察。

**判断是否增值的三个条件**（必须同时满足）：

1.  客户愿意为它付钱；
2.  它改变了产品或信息的形态；
3.  它一次就做对了。

审批、检验、搬运、等待、返工，都不满足条件，属于非增值活动——其中有些是当前条件下必要的（称为「必要的非增值」，比如法规要求的检验），应该尽量减少而不是直接取消。

## 绘制步骤

1.  **选定一个产品族或一条流程**。不要试图把所有产品画在一张图上。选一个有代表性、量又大的。
2.  **确定起点和终点**。通常是「从客户下单到客户收到」或「从需求提出到上线」。
3.  **走现场，从后往前走**。从最接近客户的环节开始倒着走，这样更容易看出每个环节是在为谁服务。
4.  **画物料流并采集数据**。每个环节记录周期时间、在制品数量、良品率。**自己掐表，不要用文档上的数字**。
5.  **画信息流**。客户需求是怎么一步步传到每个环节的？是推动式（上游做完就推给下游）还是拉动式（下游需要才做）？
6.  **画时间线，算增值比**。这是最有冲击力的一步。
7.  **标出问题点**。在图上用「爆炸符号」标注发现的问题：瓶颈、长等待、高返工率。
8.  **画未来图**。设计一个减少等待、缩短前置时间的目标状态。
9.  **制定行动计划**。未来图要拆成几个有负责人、有期限的改进项目。

**自检清单**

- [ ] 数据来自现场实测，不是文档上的标准值

- [ ] 未来图的每一项改进都有负责人和时间

## 完整案例：保险理赔流程

一家保险公司的小额家财险理赔平均需要 **21 天**，客户投诉集中在「等太久」。团队画了价值流图：

| 环节 | 实际处理时间 | 到下一环节的等待 | 问题 |
| --- | --- | --- | --- |
| 受理报案 | 15 分钟 | 1 天（当天批量转交） | 批量处理 |
| 资料初审 | 30 分钟 | 4 天（等客户补件） | 材料清单分三次发给客户 |
| 定损核价 | 45 分钟 | 6 天（等排期） | 定损员按区域排班，跨区要等 |
| 审批 | 20 分钟 | 7 天（等每周四审批会） | 所有金额都要上会 |
| 支付 | 10 分钟 | 2 天（财务批量付款） | 每周二、五两批 |
| **合计** | **约 2 小时** | **20 天** | **增值比 ≈ 0.4%** |

**关键发现**：真正的处理时间只有 2 小时，21 天里有 20 天在等待。如果按传统思路给每个环节「提效 20%」，总时长只能从 21 天降到约 20.98 天——几乎没有变化。

**未来图的三项改进**：

1.  **一次性材料清单**：受理时就把完整清单发给客户 → 消除「补件」4 天中的大部分。
2.  **授权小额直赔**：5,000 元以下由定损员直接审批，不上会 → 消除 7 天的审批等待。
3.  **每日付款**：财务改为每工作日结算一次 → 2 天降到 0.5 天。

**结果**：平均理赔时间从 21 天降到 **6 天**，人员编制不变。因为改的不是「干活的速度」，而是「等待的结构」。

## 常见误区

1.  **只画流程，不画等待**。如果图上只有处理环节，那它就是普通流程图，看不出 97% 的问题在哪。
2.  **用文档数据而不是实测数据**。流程文件上写「审批 1 个工作日」，实际可能平均 7 天。必须到现场量。
3.  **画得太细**。一张图画了 50 个环节，反而看不出重点。先画 8~12 个主要环节，有必要再对某个环节单独展开。
4.  **只画一张现状图就结束**。现状图只是诊断，未来图和行动计划才是产出。
5.  **各部门分别画自己那段**。价值流的价值恰恰在于跨部门的全貌，分段画就丢掉了交接处的等待——而那里通常是最大的问题。
6.  **优化局部**。某个环节效率翻倍，但它不是瓶颈，总前置时间可能一点没变（参见约束理论）。
7.  **一次性活动**。价值流图应该定期重画，尤其在流程发生重大变化之后。

## 价值流图与相关工具的区别

| | 价值流图 | 普通流程图 | [看板](../product_development/Kanban-Tutorial-zh.md) | [逻辑树](../problem_solving/Logic-Tree-Tutorial-zh.md) |
| --- | --- | --- | --- | --- |
| 展示什么 | 环节 + 等待 + 信息流 + 数据 | 步骤和分支 | 当前在制品的流动状态 | 问题的层级拆解 |
| 时间维度 | 有（时间线、增值比） | 无 | 实时 | 无 |
| 主要用途 | 诊断流程中的浪费 | 描述流程怎么走 | 管理日常流动 | 分析问题原因 |
| 产出 | 现状图 + 未来图 + 行动计划 | 流程文档 | 持续的流动改善 | 原因清单 |

**常见组合**：用价值流图找到结构性浪费 → 用[五问法](../root_cause_analysis/5-Whys-Tutorial-zh.md)深挖具体原因 → 用[看板](../product_development/Kanban-Tutorial-zh.md)管理改进后的日常流动 → 用 [PDCA](PDCA-Cycle-Tutorial-zh.md) 推进每一项改进。

## 常见问题

??? question "价值流图和流程图有什么区别？"

    流程图只画「做什么、按什么顺序」。价值流图额外画出**等待时间、在制品积压、信息流**，并为每个环节标注实测数据，最后算出增值比。能看出浪费在哪，是两者最大的区别。

??? question "服务业和软件开发能用价值流图吗？"

    可以，而且往往效果更明显。软件开发中它常被用来分析「从需求提出到上线」的全流程，暴露出等待评审、等待测试环境、等待发布窗口这类隐形浪费。本文的保险理赔案例就是服务业场景。

??? question "画一张价值流图需要多久？"

    一个中等复杂度的流程，通常需要一个 5~8 人的跨职能小组用 1~2 天：半天走现场采集数据，半天画现状图，半天画未来图和行动计划。

??? question "增值比低到 1% 正常吗？"

    非常常见。未经优化的流程增值比普遍在 1%~5%。这不说明员工偷懒，而说明**浪费在流程结构里，不在个人努力上**。

??? question "未来图应该设定多远的目标？"

    一般设定 6~12 个月内可达成的状态，并拆成 3~5 个可独立推进的改进项目。设得太远会变成愿景，无法落地。
